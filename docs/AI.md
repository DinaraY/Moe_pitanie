# Остаток дня и серверный ИИ

## Что работает

На странице подключения ВкусВилла есть отдельный раздел «Что съесть сегодня». Пользователь отмечает оставшиеся завтрак, обед, ужин и/или перекус. Приложение передаёт Worker только сумму КБЖУ съеденного сегодня и идентификаторы предпочтений. Сервер получает свежие реальные товары через официальный MCP, исключает недоступные/запрещённые товары и варианты без полного КБЖУ, подбирает порции и показывает полный дневной итог с учётом съеденного. Обед и ужин собираются из салата и второго либо салата и супа. Для этого профиля сочетание должно иметь известные КБЖУ, 350–600 ккал, не менее 20 г белка и не более 25 г жиров. Это практические настройки приложения, не универсальная медицинская норма. Замороженные и сырые полуфабрикаты исключаются. Порции могут быть меньше упаковки; покупки считаются упаковками с указанием остатка. В перекусах йогурты предлагаются упаковками. Диапазоны производителей сохраняются. При неизвестном КБЖУ съеденного или отсутствии подходящих вариантов расчёт не подменяется справочными/выдуманными числами.

Предлагаемые блюда можно записать в дневник и выбрать для отдельного списка покупок. В корзину попадают только эти блюда, без уже съеденного и без меню на два дня. Цены и наличие проверяются заново; создание ссылки по-прежнему требует явного подтверждения. Изменение дневника, предпочтений или оставшихся приёмов пищи делает подбор и его подтверждение устаревшими. При переходе на другую календарную дату старый подбор нельзя использовать для списка покупок/подтверждения.

Завтрак сначала собирается из яиц, свежего авокадо и овощей. Если подходящее сочетание с полными КБЖУ недоступно, сервер предлагает готовый омлет либо творог с йогуртом и показывает причину замены. Для этого профиля варианты завтрака ограничены 250–450 ккал, белком от 15 г и жирами до 25 г; порции не превышают массу упаковки (омлет — не более 300 г). Проверяется весь диапазон КБЖУ производителей. Сыр с авокадо, косметика, протёртые и маринованные томаты не считаются свежими авокадо и овощами. Эти же проверенные варианты доступны алгоритму и ИИ; модель не дописывает отсутствующие показатели. Если ни одного подходящего завтрака нет, приложение по-прежнему сообщает об отсутствии данных.

## Подключить ИИ в существующем Worker

Подключение ИИ разрешено настройкой `AI_ENABLED=true`, но остаётся недоступным без секрета `OPENAI_API_KEY`. Без настройки секретов приложение продолжает обычный подбор. Новый Worker и новая регистрация ВкусВилла не нужны.

После публикации этого изменения:

1. Открыть Cloudflare → **Workers & Pages → moe-pitanie-2 → Settings → Variables and Secrets**.
2. Добавить **Secret** `OPENAI_API_KEY` со значением своего API-ключа из OpenAI Platform. Не присылать ключ в чат и не добавлять в GitHub или клиентский JavaScript.
3. Установить обычные переменные `AI_ENABLED=true`, `AI_MONTHLY_CALL_LIMIT=100` (можно целое число от 1 до 100), сохранить и выполнить **Deploy** существующего Worker.
4. Проверить `https://moe-pitanie-2.statusdi.workers.dev/api/status`: `aiAvailable=true`. Ответ содержит только флаг готовности, не ключ.
5. На сайте подключить ВкусВилл, отметить оставшиеся приёмы пищи и согласие на передачу данных в OpenAI, нажать **«Подобрать с ИИ»**.

В репозитории флаг включения закреплён в обеих конфигурациях существующего Worker. Секрет в Git не переносится. Для остановки новых вызовов установите `AI_ENABLED=false`. Новые Worker, домены, OAuth-клиенты и базы не требуются.

Используется Responses API, фиксированная модель `gpt-6-luna`, строго структурированный ответ, `store:false`, без инструментов модели, автоматических повторов и заказов. Ей передаются дневной ориентир, диапазоны КБЖУ съеденного, номера недавних/любимых/исключённых товаров и ограниченный набор вариантов каталога с названиями, массой, КБЖУ и рейтингами. Полные записи дневника, имя/адрес пользователя, ключ OpenAI и токены ВкусВилла в запрос модели не включаются. ИИ запускается только отдельным нажатием, при сессии ВкусВилла и явном согласии.

Модель выбирает только заранее подготовленные идентификаторы вариантов. Товары, порции и КБЖУ берутся из серверного каталога, не из ответа модели. Повторяющиеся/пропущенные приёмы пищи, вымышленные варианты, отказы и незавершённые ответы отвергаются. Если вариант ИИ хуже алгоритма по дневному КБЖУ либо провайдер недоступен, возвращается обычный подбор с явной пометкой. Произвольный диалог и облачная память пока не реализованы; память дневника остаётся на устройстве.

## Контроль расходов

Атомарный счётчик в существующем Durable Object `AUTH_STORE` ограничивает **всё приложение** максимум 100 попытками обращения к модели за календарный месяц UTC (на Worker). Выход и повторный вход счётчик не сбрасывают. Лимит можно только уменьшить переменной `AI_MONTHLY_CALL_LIMIT`; некорректная настройка отключает ИИ. Каждый запрос резервирует попытку перед отправкой, неудачные запросы тоже расходуют технический лимит. Новый месяц получает новый счётчик. Максимум 24 КБ входных данных и 1200 выходных токенов на вызов; сетевой таймаут 25 секунд, ответ ограничен 64 КБ. Большие входные данные не отправляются.

Это лимит числа вызовов, **не гарантированный денежный потолок $5**: сумма зависит от тарифа провайдера и оплачивается отдельно от ChatGPT. Для финансового контроля также используются настройки проекта и баланса в OpenAI Platform; уведомление о бюджете само по себе не гарантирует остановку списаний. Реальных платных вызовов при разработке не выполнялось.

## Проверки

`npm test` включает обычный подбор, полные порции, диапазоны, неизвестные КБЖУ, исключения, атомарный лимит, запрет анонимного ИИ, обязательное согласие, структуру запроса, отклонение вымышленных вариантов и безопасный возврат к алгоритму. Браузерные проверки используют синтетический каталог и заглушку ИИ; реальную корзину и платные API они не вызывают.

Формат Responses API проверен по официальной документации: https://developers.openai.com/api/docs/guides/structured-outputs .

Поиск основных блюд, салатов и супов использует по два запроса: общий по рейтингу и уточняющий по популярности. Результаты объединяются по ID; отказ одного запроса не удаляет товары из другого. Одновременно выполняются не более двух запросов. Ограничения порционных упаковок и проверки КБЖУ действуют и для расширенного поиска.
